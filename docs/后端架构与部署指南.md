# 后端架构与部署指南（前后端分离）

> 目标：让**客户账号**与**站长管理后台**彻底分开，会员/付费校验挪到服务端，
> 客户账号 ≠ 站长账号，密码与密钥不进公开的前端 JS。

---

## 1. 架构总览

```
┌────────────────────────────┐         ┌──────────────────────────────┐
│  前端 SPA（GitHub Pages）    │         │  Cloudflare Worker（后端）     │
│  kyrie-foreign-trade-box    │  fetch  │  worker/backend.js            │
│                            │ ──────▶ │  ├─ /api/auth/*  客户账号     │
│  - 会员校验走 /api/me        │ ◀────── │  ├─ /api/me      会员快照     │
│  - 站长后台走 /api/admin/*   │  JSON  │  ├─ /api/orders* 订单         │
│  - token 存 localStorage     │         │  └─ /api/admin/* 站长后台     │
│  - 单据/跟单仍在本地浏览器    │         │        │                     │
└────────────────────────────┘         │        ▼                     │
                                       │  KV 存储（KTB_DATA）          │
                                       │  账号 / 密码哈希 / 会员状态      │
                                       │  密钥：JWT_SECRET、ADMIN_PASS  │
                                       │  （环境变量 / secret，不进前端） │
                                       └──────────────────────────────┘
```

**零成本**：Cloudflare Workers 免费额度 + KV 免费额度，足够小站使用；无数据库、无第三方依赖。

**业务数据仍留在客户端**：客户的单据、跟单记录继续存在各自浏览器 `localStorage`（天然按设备隔离、零后端成本）。后端只管**账号与会员状态**。站长不接触客户私有业务数据。

---

## 2. 账号模型

| 角色 | 存储位置 | 鉴权方式 | 谁能看 |
|------|----------|----------|--------|
| 客户 | KV `user:<username>` | HMAC token（Bearer） | 仅本人 |
| 站长 | Worker 环境变量 `ADMIN_USER` / `ADMIN_PASS` | HMAC token（Bearer, role=admin） | 仅站长本人 |

- 客户注册：**自动获得 3 天试用**（`TRIAL_DAYS`，服务端判定，无法本地篡改）。
- 密码：Web Crypto **PBKDF2-SHA256**（10 万次迭代）哈希，盐值随机，明文不落库。
- Token：HMAC-SHA256 签名、无状态、7 天有效（站长 token 1 天）。
- 会员发放：站长后台**按用户名直接开通/吊销**，取代原先可伪造的"解锁码"。

## 3. 后端接口（worker/backend.js）

| 方法 | 路径 | 说明 | 鉴权 |
|------|------|------|------|
| GET  | `/health` | 健康检查 | 否 |
| GET  | `/api/plans` | 会员方案列表 | 否 |
| POST | `/api/auth/register` | 注册（自动试用） | 否 |
| POST | `/api/auth/login` | 登录，返回 token + 会员快照 | 否 |
| GET  | `/api/me` | 当前会员快照 | 客户 token |
| POST | `/api/auth/logout` | 退出（前端清 token） | 客户 token |
| POST | `/api/auth/change-password` | 改密（重签 token） | 客户 token |
| GET  | `/api/orders` | 我的订单列表 | 客户 token |
| POST | `/api/orders` | 创建订单 | 客户 token |
| POST | `/api/orders/:id/claim` | 提交付款凭证 | 客户 token |
| POST | `/api/admin/login` | 站长登录 | 否 |
| GET  | `/api/admin/members` | 会员列表 | 站长 token |
| POST | `/api/admin/grant` | 发放会员 `{username,plan,days?}` | 站长 token |
| POST | `/api/admin/revoke` | 吊销会员 `{username}` | 站长 token |

请求/响应均为 JSON；CORS 仅放行配置的 `CORS_ORIGIN`（你的 GitHub Pages 域名）。

## 4. 部署步骤（你来执行，需 Cloudflare 账号）

> 以下命令在本地终端执行（已安装 `wrangler`：`npm i -g wrangler` 或 `npx wrangler`）。

### 4.1 创建 KV 命名空间
```bash
npx wrangler kv namespace create KTB_DATA
# 输出类似：
# { "binding": "KTB_DATA", "id": "abcd1234...." }
```

### 4.2 填写 worker/wrangler-backend.toml
把上一步拿到的 id 填到 `id = "REPLACE_WITH_KV_ID"`。
```toml
[[kv_namespaces]]
binding = "KTB_DATA"
id = "abcd1234...."   # ← 替换

[vars]
CORS_ORIGIN = "https://kyriehao-beep.github.io"   # 你的前端域名，多个逗号分隔
TRIAL_DAYS = "3"
ADMIN_USER = "admin"                              # 站长账号，多个逗号分隔
# ADMIN_PASS / JWT_SECRET 敏感，用 secret 注入（见 4.3）
```

### 4.3 注入密钥（不要写进文件）
```bash
npx wrangler secret put JWT_SECRET   # 输入一段随机串，例如 `openssl rand -hex 32`
npx wrangler secret put ADMIN_PASS   # 输入站长密码；多站长用逗号：pw1,pw2（须与 ADMIN_USER 顺序一致）
```

### 4.4 部署
```bash
npx wrangler deploy --config worker/wrangler-backend.toml
# 部署后获得 Worker 地址，例如 https://ktb-backend.<sub>.workers.dev
```

### 4.5 验证
```bash
curl https://<your-worker>/health
# {"status":"ok"}

# 站长登录（拿 token）
curl -s -X POST https://<your-worker>/api/admin/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"<你的ADMIN_PASS>"}'
```

## 5. 前端启用后端校验

在仓库根目录新建 `.env`（或被构建读取的环境）：
```
VITE_API_BASE=https://ktb-backend.<sub>.workers.dev
```
重新构建并部署 SPA：
```bash
pnpm install && pnpm run build
# 部署 dist/client 到 GitHub Pages（见下方 SPA 部署）
```
- 配了 `VITE_API_BASE` → 前端走后端校验（客户注册/登录、会员状态、站长后台全部服务端化）。
- **没配** → 前端自动退回纯本地模式（localStorage 试用演示），SPA 照常可用。

前端通过 `src/services/apiClient.ts` 的 `isBackendEnabled()` 切换；`MembershipProvider` 据此选择
`backendMembershipApi`（后端）或本地 `membershipApi`。`ProtectedFeature` 的门禁随之生效。
本地联调可用 `localStorage.ktb_api_base_override` 覆盖基地址，无需重新构建。

## 6. SPA（前端）部署

后端部署不影响前端静态托管。前端仍走 GitHub Pages：
```bash
# 将 dist/client 内容推到 gh-pages 分支（项目既有流程）
git subtree / 或克隆 gh-pages 后复制 dist/client 强制推送
```
深层路由（如 `/follow-up`）由 `dist/client/404.html` 作 SPA 回退外壳（HTTP 404 但内容为 SPA，浏览器加载后客户端路由渲染，属正常）。

## 7. 安全与成本要点

- **密钥不进前端**：`JWT_SECRET`、`ADMIN_PASS` 仅存在于 Worker 环境变量 / secret；前端只存登录 token。
- **密码不进前端**：原先 `staticConfig.ts` 里写死的 `ADMIN_PASSWORDS` 已被后端取代；本地模式仅用于演示，正式收费请用后端。
- **CORS 显式来源**：仅放行你配置的 GitHub Pages 域名，避免任意站点调用。
- **哈希与签名**：PBKDF2 防彩虹表，HMAC token 防篡改；token 过期需重新登录。
- **成本**：Workers + KV 免费额度覆盖小站；无服务器常驻费用。

---

## 8. 升级路径（可选，非必须）

- **自定义域名 + httpOnly Cookie**：当前 token 存 `localStorage`（MVP 务实方案）。若需更强 XSS 抗性，
  可在 Worker 侧改发 `httpOnly` + `Secure` + `SameSite` Cookie，并配自定义域名（避免跨站 cookie 限制）。
- **跨设备同步**：客户单据/跟单目前存本地浏览器；如需多端同步，可增一个"业务数据"KV 命名空间（按用户隔离），作为后续项。
- **邮件验证 / 找回密码**：当前为降低零成本复杂度，密码找回走站长后台人工核实；后续可接入邮件服务。
